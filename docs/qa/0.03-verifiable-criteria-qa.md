## QA verdict

**Overall result: FAIL for final Splendor0.03-dev acceptance / PR-readiness.**

The implementation has substantial passing unit, integration, TypeScript, Python, and aggregate E2E test evidence. However, the 0.03 final gate is not fully proven against `docs/rules/verifiable_criteria/kernel-e2e-through-0.03.md` because several authority and integration paths are overclaimed by the evidence report rather than proved by a single realistic runtime path.

Blocking themes:

1. Daemon run creation and resume use `WorkOrderAuthorization` metadata rather than cryptographically validating the full 0.03 `WorkOrderEnvelope` authority object.
2. Daemon runtime action/adapter/permission policy is derived from request body fields and is not narrowed from a validated full work order.
3. Remote message and state handoff authority validation also checks signature metadata presence, not full cryptographic work-order validation.
4. K-E2E-004 does not prove that placement dispatches or queues exactly one run on the selected resident instance.
5. K-E2E-008 is stitched from separate helper artifacts rather than proving a single causal 0.03 journey.
6. The E2E report can overclaim scenario assertions because `scenario()` sets all assertion booleans to `true` generically.
7. Daemon/OpenAPI run status vocabulary is not aligned with the canonical 0.03 fleet run status vocabulary.

## Bugs found

### Blocking bugs

1. **Daemon work-order acceptance is metadata-only.**
   - Paths:
     - `crates/splendor-daemon/src/lib.rs:347`
     - `crates/splendor-types/src/daemon_security.rs:706`
   - Impact: a daemon caller can satisfy run-create/resume work-order checks with arbitrary non-empty signature metadata, rather than a cryptographically valid 0.03 work order.

2. **Daemon runtime scope can be widened from request body allowlists.**
   - Path: `crates/splendor-daemon/src/lib.rs:681`
   - Impact: allowed actions/adapters/permissions are not derived from a validated signed work order, so the daemon API path does not prove work-order-scoped authority.

3. **Remote message authority is metadata-only.**
   - Path: `crates/splendor-types/src/message.rs:879`
   - Impact: a remote inbound message can be accepted with non-empty signature metadata if tenant/agent/run/scope fields match, without cryptographic work-order verification.

4. **State handoff authority is metadata-only.**
   - Path: `crates/splendor-kernel/src/state.rs:405`
   - Impact: state snapshot import/read-only reference authority can be forged unless an external layer has already performed cryptographic validation and preserved that fact.

5. **K-E2E-004 overclaims work-order dispatch.**
   - Path: `crates/splendor-daemon/tests/kernel_e2e_0_03/mod.rs:1334`
   - Impact: the scenario validates registry/placement primitives but does not dispatch a signed work order to a selected resident instance or assert exactly one queued/started run.

6. **K-E2E-008 is not a single causal journey.**
   - Path: `crates/splendor-daemon/tests/kernel_e2e_0_03/mod.rs:3207`
   - Impact: final integration acceptance is overclaimed by stitching scenario artifacts rather than executing one integrated resident/fleet run path.

7. **Scenario assertion booleans are generic.**
   - Path: `crates/splendor-daemon/tests/kernel_e2e_0_03/mod.rs:3064`
   - Impact: the evidence report can mark criteria as passed without scenario-specific proof.

### Non-blocking bugs / drift

1. `docs/milestones/0.03-dev/S1-distributed-identity-model.md:58` says TypeScript does not exist, but TypeScript packages and tests now exist.
2. The development guide lists recommended direct scenario test paths under `crates/splendor-kernel/tests` for several scenarios, while current wrapper tests live under `crates/splendor-daemon/tests`. The guide does allow existing tests to remain elsewhere, but direct reproduction commands should be updated to current paths.

## Missing tests

Required before claiming final 0.03 acceptance:

1. Daemon `POST /runs` rejects bad cryptographic work-order signatures, not only missing/empty signature metadata.
2. Daemon `POST /runs` derives `allowed_actions`, `allowed_adapters`, `allowed_permissions`, `data_refs`, and quotas from a validated signed work order and rejects request-body widening.
3. Daemon resume validates cryptographic work-order signature and run binding.
4. Remote receiver rejects bad-signature work orders using the same keyring/full-envelope validation path as 0.03-S3.
5. State handoff import/read-only reference rejects bad-signature work orders using full work-order validation.
6. Trace sync rejects scope mismatches for tenant, agent, work order, fleet, node, and instance where those fields are present.
7. K-E2E-004 proves selected resident instance receives exactly one queued/started run from the signed compatible work order.
8. K-E2E-006/K-E2E-008 prove interruption, explicit state handoff, trace sync, validated import, and resume on another compatible instance as one causal path.
9. K-E2E-008 exports a single causal graph with trace event IDs, message IDs, parent/child run IDs, state node IDs, selected instance ID, and work-order ID from the same integrated scenario.
10. Scenario assertion booleans are derived from scenario-specific checks and fail when the corresponding evidence is absent.
11. OpenAPI/TypeScript/daemon status vocabulary is parity-checked against either the canonical 0.03 run statuses or an explicit documented mapping that prevents drift.

## Required fixes before PR review

1. Replace or augment daemon `WorkOrderAuthorization` with a cryptographically validated `WorkOrderEnvelope`/`ValidatedWorkOrder` authority path for create/resume.
2. Derive runtime allowed actions/adapters/permissions/data refs/quotas from the validated work order; reject any request-body widening.
3. Apply the full validated-work-order model to remote message accept and state handoff import/reference paths, or pass a non-forgeable `ValidatedWorkOrder` marker produced by the keyring validation layer.
4. Bind trace-sync scope to authenticated source identity and reject scope/payload mismatch for tenant, agent, work order, fleet, node, and instance fields when present.
5. Update K-E2E-004 to perform actual resident dispatch/queue/start evidence after placement selection.
6. Replace stitched K-E2E-008 evidence with a single integrated journey that follows one causal path across daemon work-order submission, placement, resident dispatch, local delegation, remote message, gateway allow/deny, state commit, interruption, handoff/resume, replay, and telemetry.
7. Make the E2E report assertions scenario-specific and evidence-derived rather than defaulting all booleans to `true`.
8. Align daemon/OpenAPI/TypeScript run status vocabularies with the canonical 0.03 fleet status set, or document and test a deliberate compatibility mapping.
9. Update stale docs noted above.

## Future sprint scope check

No direct implementation changes were made by this QA task. The reviewed implementation does include 0.04/0.05-looking modules and examples in the repository, but the 0.03 E2E non-goals remain mostly respected by the specific 0.03 harness:

- no full enterprise SaaS UI;
- no distributed consensus engine;
- no arbitrary shared distributed memory;
- no physical/edge safety verifier or robotics adapter required for 0.03 acceptance;
- no telemetry-as-authority in the 0.03 telemetry collector tests.

The main acceptance blockers are not future-scope leakage; they are insufficient proof and authority-boundary gaps in the 0.03 integration surface.

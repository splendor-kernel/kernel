# Migrating From 0.01-dev Through 0.05-dev To 0.1-dev

This guide maps the development milestone schema/API vocabulary to the stable
0.1 primitive line. It is a compatibility and migration guide, not an automatic
state/trace rewrite tool.

Migration must not authorize side effects, grant approvals, issue work orders,
alter live state heads, rewrite trace identity as a new concept, or execute
adapters. Replay remains inspect-only by default.

## Migration Principles

- Emit stable 0.1 field names in new data.
- Accept dev-era aliases only where implementations explicitly document input
  compatibility.
- Preserve identity separation across tenant, agent, run, action, state, trace,
  message, work order, approval, fleet, node, and instance fields.
- Treat unknown top-level fields as non-stable. They may be rejected or preserved
  as inert metadata, but must not affect authorization, verification, quotas,
  gateway routing, work-order scope, approval state, or adapter selection.
- Route side effects through the Action Gateway after verifier evaluation. Do not
  migrate old direct adapter examples into stable docs unless they use the
  gateway.

## Field And API Mapping

| Dev-era field or API | Stable 0.1 replacement | Migration guidance |
| --- | --- | --- |
| `trace_id` on serialized trace records | `trace_event_id` | Emit `trace_event_id`. Accept `trace_id` only as an input alias where implemented. Do not treat both fields as distinct identities. |
| TypeScript `TraceId` alias | `TraceEventId` | Keep source-compatible imports where present, but update stable examples and docs to `TraceEventId`. |
| Public wording `StateCommit.node_id` | `state_node_id` | Public schemas and release docs use `state_node_id`. Rust implementation internals may retain local field names if serialization preserves the stable schema. |
| State commit records without tenant/run/trace linkage from early local fixtures | `StateNode` with `tenant_id`, `agent_id`, `run_id`, `parents`, `state_hash`, `created_at`, and optional `trace_event_id` | Re-export or regenerate fixtures with explicit state ownership and trace linkage before claiming 0.1 compatibility. Do not infer missing tenant/run authority from process context. |
| Early local trace logs treated as diagnostic logs | Stable `TraceEvent` runtime-contract records | Preserve append-only ordering and identity. Trace events prove runtime transitions; they are not optional logs. |
| Direct local adapter/tool examples from 0.01-era documentation | `ActionRequest` through Action Gateway and verifier chain | Rewrite examples so policies propose actions and adapters execute only after gateway verification. |
| Local quickstart runs without work-order authority | Signed `WorkOrderEnvelope`; local-only `allow_unsigned_local_run: true` remains explicit dev mode | Use signed scoped work orders for daemon/resident/fleet examples. Keep unsigned local mode only for explicit local quickstarts with visible warning and no production claim. |
| `WorkOrderAuthorization.allowed_scopes` as a broad run authority description | `WorkOrderEnvelope` fields: `allowed_actions`, `allowed_adapters`, `allowed_permissions`, `data_refs`, `quotas`, `placement`, `expires_at`, `revocation`, `signature` | Replace broad scope lists with explicit work-order fields. Endpoint scopes authorize daemon API calls; work-order fields authorize run scope; gateway/verifiers authorize side effects. |
| Treating caller token, daemon token, or API key as action authority | Layered daemon security plus gateway verification | Caller credentials authenticate apps and endpoint scopes. They never replace signed work orders or Action Gateway authorization. |
| Daemon request examples with `credential: null` for production-like calls | Non-null `CallerCredential`, `AuditAttribution`, endpoint scopes, and signed `WorkOrderEnvelope` | `credential: null` is not a stable production pattern. Local insecure mode must be explicit, loopback or Unix-socket-bound, visibly warned, and never a silent SDK fallback. |
| Endpoint scope spellings such as `runs_create` in local fixtures | Documented endpoint scopes such as `splendor.runs.create` | Stable docs should use the endpoint-scope vocabulary in `docs/reference/daemon-security-boundary.md` and `docs/spec/0.1/api-stability.md`. Where current tests use local enum spellings, treat them as implementation mapping details. |
| Python-local lowercase action statuses such as `executed`, `denied`, `failed`, `needs_approval`, `needs_intervention` crossing daemon boundaries unchanged | Stable daemon/API outcome statuses `Executed`, `Denied`, `Failed`, `NeedsApproval`, `NeedsIntervention` | Normalize at daemon/client boundaries. Keep lowercase only for documented Python-local SDK behavior. Do not mix case in wire examples. |
| Daemon status/version metadata implying active 0.1 negotiation | Documentation that version headers are advisory in the current daemon | Stable clients may send `X-Splendor-API-Version: 0.1`, but the daemon does not yet actively negotiate or reject unsupported versions. Compatibility is proven through docs, OpenAPI review, client tests, and conformance fixtures. |
| TypeScript packages as runtime enforcement or policy execution surfaces | TypeScript `@splendor/types` and `@splendor/client` as control-plane/client surfaces | Keep runtime enforcement in Rust. TypeScript must not execute gateways, verifiers, adapters, state commits, trace writes, or replay. |
| Message payloads used as delegated permission containers | `Message` plus scoped work order or delegated authority records | Messages carry coordination data and causal parents. They do not grant permissions or widen work-order scope by themselves. |
| Local delegation inheriting parent/caller permissions by default | Parent/child run metadata with scoped delegated permissions and work-order bounds | Specialist or shared agents must receive narrower explicit authority. Do not launder parent permissions through messages or child runs. |
| Placement v0 interpreted as production fleet scheduling | Placement hints/capability matching reference path | Keep placement v0 as a foundation. It is not autoscaling, production fleet scheduling, multi-region optimization, or distributed consensus. |
| Remote message transport interpreted as mature multi-host broker | Trace-linked remote message transport foundation | Preserve message identity and delivery failure states, but do not claim production broker semantics unless separately implemented and validated. |
| Trace aggregation interpreted as production central trace service | Local buffer/sync/index reference path with hash-chain validation | Do not claim a managed trace product, long-term warehouse, or observability platform. |
| State handoff interpreted as distributed shared mutable memory | Explicit snapshot export/import, read-only references, and state-head validation | Do not introduce hidden shared mutable state, CRDTs, arbitrary merges, or automatic conflict resolution. |
| Governance approval objects treated as gateway bypass tokens | Approval evidence evaluated by approval verifier and gateway | Approval can remove a block within scope; it cannot bypass tenant, work-order, permission, quota, data-scope, safety, or postcondition checks. |
| Kill-switch state treated as implemented fleet propagation | Governance state/trace model only unless central propagation is separately documented | 0.1 does not claim production central kill-switch propagation to resident instances. |
| Policy bundle metadata carrying credentials or broad authority | Signed policy bundle/cache metadata plus explicit work-order/gateway checks | Policy TTL/revocation can deny or degrade. Policy metadata must not smuggle credentials, signatures, work orders, approvals, or permissions. |
| Adapter maturity levels as certification or marketplace approval | Evidence-based maturity metadata: `experimental`, `local-safe`, `network-safe`, `governance-aware`, `device-safe` | Maturity is a technical evidence model. It does not certify production readiness, legal compliance, vendor approval, or physical safety. |
| Physical action names for raw motors, actuator writes, firmware safety bypass, or collision-avoidance bypass | High-level bounded actions such as `read_battery`, `read_sensor_summary`, `move_to_waypoint`, `return_to_base`, `dock`, `inspect_zone`, `pause_mission`, `request_operator_override` | Reject forbidden direct physical actions before adapter execution. Splendor remains above real-time controllers and middleware. |
| Cloud helper output as direct actuator authority | Advisory plan/artifact/message that local device Splendor validates before bounded actions | Cloud helpers propose. Local device gateway and safety verifiers remain authoritative. |
| Replay modes that re-run filesystem, network, governance, or physical adapters by default | `inspect_only` replay with `side_effects_replayed: false` | Any safe simulation mode must be explicitly gated and separate. Migration must not re-execute side effects. |

## Removed Or Not Stabilized

| Dev-era surface | 0.1 status | Reason |
| --- | --- | --- |
| Anonymous non-dev daemon calls | Not stable and must fail closed | Daemon APIs are security boundaries requiring caller authentication and endpoint scopes. |
| Unauthenticated remote TCP daemon listener | Not stable | Local insecure mode is explicit and loopback/Unix-socket constrained only. |
| Broad inherited permissions for shared agents or tools | Removed as an allowed behavior | Prevents permission laundering. Delegation must be scoped. |
| Direct side-effectful policy code | Not stable | Python policy code proposes actions; gateway/verifiers/adapters enforce execution. |
| Production fleet scheduler/autoscaler | Not stable | 0.03 foundations exist, but production scheduling is future work. |
| Production adapter certification/marketplace | Not stable | 0.1 defines maturity metadata and validation, not a certification program. |
| Production robotics or live hardware readiness claim | Not stable | 0.05 physical/edge work is contract and simulation focused. |
| Hard real-time robot/device control | Forbidden as Splendor direct behavior | Real-time controllers, firmware, PLCs, ROS/native drivers, and middleware remain authoritative below Splendor. |

## Migration Checklist

1. Update serialized traces to emit `trace_event_id`.
2. Update public state references to `state_node_id` and include tenant, agent,
   run, parent, hash, timestamp, and trace linkage where applicable.
3. Replace broad authorization or scope aliases with explicit
   `WorkOrderEnvelope` fields.
4. Keep caller credentials, endpoint scopes, signed work orders, tenant/run
   checks, and gateway verification as separate layers.
5. Normalize daemon/API outcome status casing at language boundaries.
6. Replace production-like `credential: null` examples with explicit local-dev
   warnings or real caller credential shapes.
7. Move non-authorizing metadata into documented `extensions` objects and verify
   extension keys cannot grant authority.
8. Re-run conformance and adapter manifest validation:

```bash
python conformance/0.1/run-conformance.py
python scripts/validate-adapter-manifests.py
```

# Splendor 0.05-dev Release Notes

## Status

0.05-dev is the physical and edge orchestration development release. It builds on
the 0.01 local kernel baseline, 0.02 local multi-agent and daemon-control surface,
0.03 resident/fleet foundation, and 0.04 governance workflows. The release adds
device profiles, offline policy cache behavior, local trace buffering and
reconnect sync, a high-level robotics adapter contract, physical safety verifier
API, advisory cloud-helper pattern, and a simulation harness that proves these
contracts without live hardware.

The release remains a development milestone, not the 0.1 stable compatibility
line and not a production robotics certification claim.

## Implemented Primitives

- Device profile and physical capability contracts for robots, drones, humanoids,
  edge appliances, desktop sidecars, and industrial devices. Capability validation
  rejects raw motor/actuator or ambiguous physical actions as direct Splendor
  actions.
- Offline policy cache behavior for resident physical/edge instances. Explicitly
  allowed low-risk actions can continue within cached policy TTL while high-risk,
  unspecified, expired, revoked, or missing-policy cases deny or require local
  intervention before adapter execution.
- Local trace buffer and reconnect sync semantics for disconnected nodes,
  including offline interval markers, sync boundaries, duplicate sync handling,
  corruption quarantine/rejection, and storage-pressure fail-closed behavior for
  side-effectful actions.
- High-level robotics adapter contract and simulated robot/drone adapter for
  bounded mission actions such as `read_battery`, `read_sensor_summary`,
  `read_map`, `move_to_waypoint`, `return_to_base`, `dock`, `inspect_zone`,
  `capture_image`, `pause_mission`, `resume_mission`,
  `request_operator_override`, `notify_operator`, and `upload_trace_summary`.
- Physical safety verifier API integrated into the existing gateway verifier
  chain, with simulated evidence for geofence, battery, emergency stop,
  collision, altitude, privacy, proximity, uncertainty, and postcondition checks.
- Advisory cloud-helper pattern. Helper work orders and route-plan proposal
  messages cannot carry direct physical or robotics adapter authority; local
  device validation converts accepted proposals into bounded local action
  candidates that still require gateway and safety-verifier approval.
- Physical simulation harness covering successful high-level missions, forbidden
  low-level action denial, safety denial before adapter execution, offline interval
  reconnect sync, operator intervention/override request flow, cloud-helper local
  validation, final state heads, and inspect-only replay.

## User-Visible Commands And Packages

```bash
splendorctl --version
splendorctl run --config <path> [--cycles <n> | --forever]
splendorctl trace export --db <trace-db> --run <run-id>
splendorctl state head --db <trace-db> --run <run-id>
splendorctl replay --db <trace-db> --state-db <state-db> --run <run-id>
splendorctl audit export --db <trace-db> --state-db <state-db> --run <run-id>
splendor-daemon
cargo test -p splendor-kernel physical_harness --no-default-features
docker pull ghcr.io/splendor-os/kernel:0.05-dev
docker run --rm ghcr.io/splendor-os/kernel:0.05-dev
```

The Docker image is a local/dev smoke-test packaging surface for the runtime,
CLI, daemon binary, Python SDK, and examples. It is not a production remote daemon
deployment and not a physical hardware deployment image.

TypeScript packages remain control-plane/client surfaces:

- `@splendor/types`
- `@splendor/client`

## Compatibility Notes

- Rust, Python, and TypeScript package versions currently report `0.1.0`; the
  milestone release label is `Splendor0.05-dev`.
- Public schemas remain development-stage and provisional until the 0.1 stable
  primitive spec.
- TypeScript packages do not execute policies, verifiers, gateways, adapters,
  state commits, trace writes, or replay. Runtime enforcement remains in Rust.
- 0.05 physical/edge contracts build on existing 0.03 identity/work-order/message
  and trace foundations plus 0.04 policy/governance primitives. They do not create
  a separate physical execution path.
- Physical actions must remain high-level, bounded, gateway-mediated, and
  safety-verifier checked before adapter execution.
- Replay remains inspect-only for physical/edge scenarios and must not re-contact
  cloud helpers or execute robotics adapters by default.
- The Docker image is a deployment/install artifact for local runtime smoke tests.
  The included daemon remains explicit local-only insecure development mode and
  must not be exposed as an unauthenticated remote service.
- Release image manifests are documented for `linux/amd64` and `linux/arm64`;
  other architectures are not part of this release line.

## Explicitly Not Included

- No hard real-time robot control, motor control, raw actuator writes, firmware
  safety bypass, flight-controller replacement, PLC replacement, low-level
  collision avoidance, low-level sensor fusion, or production robotics safety
  certification.
- No production ROS package, native device-driver implementation, hardware adapter
  discovery framework, live flight testing, or live hardware readiness claim.
- No cloud teleoperation or direct cloud-to-actuator authority. Cloud helpers are
  advisory by default and local device Splendor validation remains authoritative.
- No fleet route optimizer product, physical operations UI, enterprise SaaS UI,
  approval queue product, marketplace, billing, or adapter certification program.
- No distributed consensus, arbitrary shared mutable distributed memory, mature
  multi-region fleet scheduler, production PKI/key management, or 0.1 stable
  compatibility guarantee.

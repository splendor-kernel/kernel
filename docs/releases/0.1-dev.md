# Splendor 0.1-dev Release Notes

## Status

Splendor 0.1-dev is the first stable primitive compatibility line for the
kernel runtime contracts implemented across the 0.01-dev through 0.05-dev
milestones. It freezes documented primitive schemas, SDK/API compatibility
boundaries, adapter maturity evidence, operational guides, conformance fixtures,
and migration policy.

This is not a 1.0 production release, enterprise support policy, production fleet
scheduler, production remote daemon, adapter marketplace, adapter certification
program, production robotics safety certification, or hard real-time controller.

## Stable 0.1 Primitives

The stable primitive surface is documented in `docs/spec/0.1/primitives.md` and
includes:

- Tenant, Agent, Run, Tick, Action, Percept, Message, StateNode, TraceEvent, and
  WorkOrder.
- Approval, Policy, Constraint, Verifier, Adapter, Feedback, and Reward.
- Distinct identity fields for fleet, node, instance, tenant, agent, runtime
  context, run, tick, action, state node, trace event, message, work order,
  approval, and artifact scope.
- Non-authorizing extension rules that prevent extension metadata from granting
  actions, adapters, permissions, approvals, credentials, work orders, policies,
  quotas, or verifier outcomes.
- Replay defaults that inspect or simulate recorded evidence without executing
  adapters or external side effects.

## Stable SDK And API Surface

The 0.1 SDK/API compatibility boundary is documented in
`docs/spec/0.1/api-stability.md`.

- Rust stable items are limited to the exported crates and types named in the API
  stability document.
- Python stable local SDK surface is limited to `KernelRuntime`, stable runtime
  config/types/constants, and the named local methods.
- TypeScript stable surface is `@splendor/types` and `@splendor/client` as a
  daemon client/control-plane surface only.
- Runtime daemon stability covers the local daemon endpoint names, stable error
  shapes, and layered security boundary documented in
  `docs/reference/runtime-daemon-api.md`.

Stable daemon communication must preserve this order:

```text
transport security -> caller authentication -> endpoint scopes -> signed work order -> tenant/agent/run checks -> gateway verification
```

A caller credential authenticates the app. A signed work order authorizes run
creation or resume. The Action Gateway authorizes side effects.

## User-Visible Commands And Examples

From a fresh checkout, start with the stable local runtime and daemon operation
guides:

```bash
cargo build -p splendorctl
./target/debug/splendorctl run --config ./examples/local-basic-loop/config.yaml --cycles 1
./target/debug/splendorctl replay --db ./examples/local-basic-loop/data/trace.db --state-db ./examples/local-basic-loop/data/state.db --run 22222222-2222-2222-2222-222222222222
```

The complete local smoke path remains:

```bash
bash scripts/verify-0.01-baseline.sh
```

Daemon example validation is test-backed:

```bash
cargo test -p splendor-daemon
```

## Compatibility Notes

- `trace_event_id` is the stable trace identity field. `trace_id` is only a
  dev-era input compatibility alias where accepted.
- Stable public serialized fields use snake_case unless an SDK-local surface
  explicitly documents a local-only representation.
- Daemon gateway outcomes use PascalCase statuses in the stable daemon surface;
  Python-local runtime statuses may remain lowercase/local-only and should be
  normalized at daemon or cross-language boundaries.
- The current TypeScript client can send `X-Splendor-API-Version`, but daemon
  route implementation does not actively negotiate versions or reject unsupported
  version headers. This is a documented limitation, not a production protocol
  guarantee.
- `allow_unsigned_local_run: true` is local-development-only. Stable daemon and
  resident/fleet examples must preserve caller credential, endpoint scope, signed
  work-order, and gateway enforcement.

## Experimental Or Future Work

The following remain experimental, development-only, or future work unless later
release notes explicitly stabilize them:

- Production remote daemon authentication, fleet mTLS/OIDC rollout, node
  bootstrap, remote fleet scheduling, autoscaling, multi-region placement, and
  distributed consensus.
- Production adapter certification, legal/vendor approval, adapter marketplace,
  and enterprise support policy.
- Approval UI, enterprise IAM integration, broad workflow engine, billing,
  marketplace, admin console, or product-specific Harmony implementation.
- Native Node/N-API binding, browser runtime execution, and TypeScript runtime
  enforcement.
- Live hardware readiness, ROS/native device-driver implementation, hard
  real-time robot control, motor control, firmware safety bypass, flight
  controller replacement, PLC replacement, or production robotics safety
  certification.

## Operating constraints for sub-agent work

- Master loop agent does not write production implementation code; implementation/test/docs edits are delegated to sub-agents.
- Acceptance scenarios must exercise documented public surfaces: daemon API, CLI, Python SDK, TypeScript client, OpenAPI-derived contract checks, fleet/management API, and adapter interfaces. Private Rust helpers cannot be used to claim E2E correctness.
- External services may be deterministic fakes only beyond Splendor adapter boundaries. Gateway, verifier, state graph, trace store, replay, message, work-order, governance, and public API contracts must not be mocked away.
- Every scenario must produce positive, negative/fail-closed, replay/audit, trace/state, API/compatibility, and anti-drift evidence appropriate to its scope.
- No acceptance credit for chat-first UX, enterprise SaaS UI, marketplace, universal memory, bare-metal OS, full consensus, or real-time robotics controller behavior.
- Replay must suppress side-effectful adapters by default.
- Management/caller credentials, work orders, and gateway authority must remain separate.
- Telemetry, health, and capabilities remain non-authoritative.
- Physical/edge scenarios may use only high-level bounded actions and must reject raw actuator or firmware-bypass actions.

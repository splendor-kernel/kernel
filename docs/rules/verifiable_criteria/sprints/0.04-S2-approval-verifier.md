# 0.04-S2 — Approval verifier

**Milestone:** Splendor0.04-dev

**Objective:** Require, pause for, validate, and apply approvals for scoped actions and runs through the verifier chain.

**Amendment status:** Required resident approval remediation contract target;
unchecked until implementation and retained evidence land.

**Bounded scope**

- Implement approval-required detection.
- Pause run/action when approval is missing.
- Re-evaluate the exact pending action from a trusted receipt, or fail closed on
  denial/expiry/mismatch.
- Reject raw approval evidence before gateway, runtime trace, and lifecycle
  mutation except for an exact stored `WaitingForApproval` `/actions` retry that
  carries denial, expiry, or revocation only.
- Bind secure resident receipts to exact target instance plus run, and bind
  physical approval to a server-derived typed `NodeId` resource coordinate.
- Revoke a granted resident receipt only through the authority-owned ledger and
  an authenticated exact-target resident acknowledgement.

**Functional outputs**

- Approval verifier.
- Exact approval challenge and trusted receipt validation.
- Run pause/exact-action-retry integration.
- Versioned resident receipt revocation request/acknowledgement contract.
- Tests for grant, denial, expiry, revocation, and wrong scope.

**Verifiable acceptance criteria**

- [ ] An action requiring approval returns needs_approval and does not execute the adapter.
- [ ] The run enters waiting_for_approval or equivalent paused state with trace linkage.
- [ ] A raw granted `ApprovalEvidence` cannot authorize execution.
- [ ] Raw granted evidence, and raw evidence of any decision on an active run,
  is rejected before gateway invocation, runtime trace append, approval pause,
  or any lifecycle mutation.
- [ ] The only raw-evidence exception is the exact stored
  `WaitingForApproval` `/actions` retry carrying no receipt and representing
  denial, expiry, or revocation; it remains fail-closed with zero adapter calls.
- [ ] A trusted receipt for the exact challenged action permits re-evaluation and one execution.
- [ ] Changed action parameters or replayed/semantically reissued receipts are rejected.
- [ ] Approval for a different tenant, agent, action, adapter, or expired window is rejected.
- [ ] Approval denial or expiry fails closed, not as a silent retry or permissive lifecycle resume.
- [ ] Secure resident receipt audience v2 binds the exact trusted `InstanceId`
  and `RunId`; a run-only v1 audience, wrong instance, wrong run, or caller-
  supplied target coordinate is rejected.
- [ ] Physical approval digests include the server-derived typed `NodeId`/
  physical resource coordinate under the physical v2 domain. Params, metadata,
  body fields, and mirrors cannot set or override it; nonphysical v1 digest bytes
  remain unchanged.
- [ ] Outstanding physical v1 challenges cannot authorize an effect and must be
  re-challenged under physical v2 without receipt translation.
- [ ] Grant, retain the exact receipt/target, revoke with an authenticated exact-
  target resident acknowledgement, then retry the action: the resident returns
  `revoked` or `already_revoked` and adapter effect count remains zero.
- [ ] Concurrent revoke versus gateway claim has exactly one authority-ledger
  winner: revoke-first prevents execution; claim-first yields resident
  `already_claimed` and manager `too_late`, never successful revocation.
- [ ] Revocation sent to the wrong node/instance is rejected without a tombstone;
  a fresh-JTI request to the original exact node/instance can then succeed.
- [ ] Dedicated resident revocation scope, TLS/hostname, exact-origin, closed
  request/response, and one-use JTI are enforced. JTI replay, wrong scope,
  timeout, reset, malformed response, or target mismatch cannot report success;
  post-send uncertainty is explicit.
- [ ] Replay explains why approval was required and what grant/denial changed the outcome.

**Integration constraints**

- Approval is a verifier/gateway concern. External systems may issue approval objects but cannot bypass gateway execution.
- Ownership remains daemon authentication/translation -> kernel lifecycle and
  pending challenge -> Authority Service audience/digest/claim/revoke ledger.
- Do not implement broad workflow orchestration in the verifier.

**Explicit non-goals**

- No approval queue UI.
- No human notification system.
- No workflow DSL.
- No production PKI, restart-durable receipt ledger, durable revocation watch,
  external introspection, or broad manager authentication claim.
